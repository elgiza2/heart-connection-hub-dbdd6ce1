# خطة: تحويل الوكيل إلى وكيل كامل (مستوى Manus)

الهدف: الوكيل ينفّذ **أي** مهمة داخل نفس الشات — برمجة، تكاملات، MCP، تشغيل كود، إنتاج ملفات، وتشغيل المتصفح عند الحاجة — يكمّلها لآخرها حتى لو أخذت ساعات، ويقول للمستخدم صراحة "دلوقتي بأراجع اللي عملته" ثم يراجع ويصلّح.

## ١. تصنيف المهمة قبل التنفيذ
- المخطِّط (`agent_plans`) يرجع الآن `kind`:
  - `browser` = المهمة كلها تشغيل واجهة موقع (تسجيل دخول، فورمات، كليك).
  - `agentic` = كل الباقي: برمجة، بيانات، ملفات، APIs، MCP، ومهام مختلطة.
- المهام المختلطة تبدأ `agentic`، والوكيل نفسه يسلّم جزء المتصفح لأداة `browser_task`.

## ٢. المُنفِّذ الوكيلي (ReAct server-side)
ملف جديد `_shared/agentkernel/executor.ts`: كل دورة يختار الموديل **أداة واحدة** بقرار منه، وتُسجَّل الملاحظة في `long_run_events`، فتكمل المهمة عبر عدة ticks بدون فقدان السياق.

الأدوات:
| الأداة | الاستخدام |
| --- | --- |
| `run_code` | تشغيل JavaScript/TypeScript حقيقي في Worker معزول (بدون صلاحيات) لتحليل البيانات، الحسابات، توليد الملفات |
| `mcp_call` / `list_mcp_tools` | التكاملات: نداء أدوات سيرفرات MCP المربوطة للمستخدم من `mcp_connections` عبر JSON-RPC |
| `write_file` / `read_file` | إنتاج وقراءة مخرجات (كود، تقارير، CSV) قابلة للتحميل |
| `web_search` | البحث عند الحاجة فقط، مش هدف المهمة |
| `browser_task` | تسليم جزء واجهة الموقع للمتصفح السحابي |
| `remember` | تخزين معرفة دائمة في `agent_memory` |
| `ask_user` | يوقف ويسأل: CAPTCHA، OTP، بيانات دخول، دفع، إجراء غير قابل للتراجع، هدف غامض |
| `finish` | الإنهاء فقط بعد التحقق الفعلي |

## ٣. المراجعة الذاتية المعلنة
- عند `finish` يتحوّل الـrun إلى مرحلة `reviewing` مع `status_text` معلن: "بأراجع اللي عملته" — يظهر في الشات فورًا.
- المراجع يقارن الهدف + معايير النجاح + كل الـtranscript + المخرجات، ويحكم: `pass` / `retry` / `ask`.
- `retry` يرجع لنفس اللوب بتوجيه تصحيحي (حتى ٣ جولات)، `ask` يوقف ويسأل، `pass` ينهي بملخّص + المخرجات.

## ٤. الاستمرارية والمهام الطويلة
- ميزانية افتراضية ٦ ساعات، حتى ٦٠٠ خطوة، checkpoints كل خطوة.
- كل tick محدود (عدد خطوات + مهلة زمنية) وبيقفل الـrun على نفسه (single-flight) عن طريق `last_heartbeat_at`، وبيكمل من نفس النقطة في الtick اللي بعده.
- كشف التكرار (fingerprint + strikes): يغيّر الطريقة، ولو فضل عالق يسأل المستخدم.
- إشعار عند الانتهاء أو عند الحاجة لتدخّل، وكل ده شغّال والتاب مقفول.

## ٥. واجهة الوكيل داخل نفس الشات
- فصل **المحادثة** عن **مسرح التنفيذ**: الشات يعرض القرارات والنتيجة، وبانل جانبي يعرض المتصفح، الطرفية، الملفات، والـdiffs.
- خطة حيّة كـchecklist قابلة للتعديل والترتيب، بثلاث حالات: منتظرة / جارية / مكتملة، مع عدد الخطوات والوقت المنقضي دون ETA أو نسبة وهمية.
- Agent trace مطوي افتراضيًا: صف لكل أداة بأيقونة ثابتة، الحالة، والهدف المختصر؛ stdout والـHTML والمعاملات والـdiffs الكبيرة تظهر عند التوسعة فقط.
- الأخطاء، طلبات المستخدم، ونقاط الموافقة تظل ظاهرة وغير مطوية. الرسالة النهائية ملخص وتسليمات، وليست تفريغًا للسجل.
- عرض المتصفح حيًا مع زر «خُد التحكم» عند CAPTCHA أو تسجيل الدخول أو 2FA، ثم «استئناف» من نفس الجلسة.
- المخرجات تظهر كـchips وبانل مستقل: ملفات قابلة للتحميل، diffs، نتائج اختبارات، وروابط التكاملات.

## ٦. الموافقات والتحكم البشري
- الاستمرار التلقائي بعد ٦٠ ثانية مسموح فقط للقراءة، البحث، التحليل، والخطوات القابلة للتراجع منخفضة الأثر.
- لا عدّاد ولا تجاوز تلقائي للدفع، الشراء، الحذف، الإرسال الخارجي، تغيير الصلاحيات، النشر، push لبيئة مشتركة، CAPTCHA، تسجيل الدخول، OTP أو 2FA.
- الأفعال الحساسة تعرض بالضبط: الفعل، الهدف/المستلم، المبلغ أو نطاق التأثير، والـdiff عند وجوده، ثم تتطلب موافقة صريحة server-side.
- الخطة لها «متابعة» و«تعديل الخطة»؛ تعديل أي خطوة يلغي الاعتماد التلقائي حتى يراجع الوكيل التعديل ويؤكد فهمه.
- الأسئلة تكون محددة بخيارات واقتراح افتراضي كلما أمكن، مع حفظ سبب التوقف والسياق الكامل للاستئناف.

## ٧. التوجيه والإيقاف أثناء العمل
- **توجيه عند نقطة آمنة**: الوضع الافتراضي؛ يدخل التوجيه بين استدعاءات الأدوات دون إهدار العمل الحالي.
- **إضافة للطابور**: رسالة تنتظر اكتمال الدورة الحالية، مع شارة واضحة بعدد الرسائل.
- **إيقاف ناعم**: يتوقف عند أقرب checkpoint ويحفظ المخرجات الجزئية.
- **إيقاف فوري**: للحالات الحرجة فقط، مع بيان ما تم حفظه وما قد يكون غير مكتمل.
- لا تخلط الواجهة بين queued وsteering؛ لكل وضع اسم وحالة بصرية واضحة.

## ٨. المهام الطويلة والإشعارات
- `long_runs` هو مصدر الحقيقة server-side؛ إغلاق الصفحة أو انقطاع الاتصال لا يوقف المهمة.
- الاستئناف من آخر checkpoint ناجح دون إعادة الخطوات المكتملة، مع إمكانية تغيير التوجيه عند الاستئناف.
- قائمة Runs مركزية قابلة للفلترة: تعمل / تحتاج تدخلك / متوقفة / مكتملة / فشلت / أُلغيت، مع آخر نشاط والوقت المنقضي.
- إشعار فوري عند الحاجة للمستخدم، الفشل، أو الاكتمال؛ تحديثات التقدم الروتينية تُجمع لتجنب الإزعاج.
- الاحتفاظ بالـtranscript والمخرجات الجزئية بعد الفشل أو الإلغاء لإعادة المحاولة أو المراجعة.

## ٩. المراجعة الذاتية والتسليم
- قبل التسليم يظهر في الـtrace: «دلوقتي بأراجع اللي عملته».
- المراجعة تشغّل تحققًا مناسبًا للمهمة: build/tests/lint، فحص الملفات، إعادة قراءة نتائج API، أو screenshot نهائي للمتصفح.
- قسم النتيجة يفرّق بين: تحقق آلي ناجح، تحذيرات، وافتراضات لم يمكن إثباتها.
- عند فشل المراجعة: إصلاح وإعادة تحقق حتى ٣ جولات؛ بعدها سؤال المستخدم أو تسليم واضح بما تعذر، لا ادعاء نجاح.

## ١٠. مراحل التنفيذ
1. تثبيت عقدة الحالات والموافقات server-side، وإكمال استهلاك الـticks والـcheckpoints والـlocks.
2. إكمال حلقة الأدوات الحقيقية للبرمجة والملفات وMCP والمتصفح، مع حدود صلاحيات وأحجام ووقت واضحة.
3. إكمال واجهة الشات: checklist، trace، التوجيه، takeover، المخرجات، وحالات الخطأ والموافقة.
4. إضافة قائمة Runs والإشعارات والاستئناف والإلغاء المتدرج.
5. اختبارات end-to-end لمهمة برمجة، تكامل MCP، مهمة متصفح تحتاج takeover، ومهمة تستمر بعد إغلاق الصفحة.
6. اختبار المراجعة الذاتية عمدًا بحالة تفشل أول مرة ثم تُصلح وتُراجع.
7. نشر `long-run` واختبار call حقيقي، ثم تحويل cron من `agent-tick` إلى action `cron_tick` المدمج فقط بعد نجاح النشر.

## ١١. معايير القبول
- ينفّذ الوكيل البرمجة والتكاملات وMCP والملفات والمتصفح، والبحث أداة مساعدة لا نوع المهمة الوحيد.
- يكمل run بعد إغلاق التبويب، ويعود من checkpoint بعد الانقطاع، ولا يكرر الفعل الفاشل بلا تغيير.
- لا ينفذ فعلًا حساسًا دون موافقة صريحة، ولا يطلب كلمة مرور داخل الشات.
- يعرض تقدمًا صادقًا، trace قابلًا للفحص، ومخرجات قابلة للتحميل.
- يعلن المراجعة ويقدّم دليل تحقق فعلي قبل إعلان النجاح.

## ملاحظة تشغيلية مهمة
نشر Edge Functions ما زال يفشل من منصة Supabase برسالة `An internal error occurred` حتى للدوال القديمة، وآخر محاولة لنشر `long-run` فشلت دون نشر أي دالة. الخطأ ومتطلب إعادة النشر محفوظان في الذاكرة الدائمة. يجب نشر `long-run` (وبداخلها `cron_tick`) فور عودة القناة، اختبار الاستدعاء الحقيقي، ثم فقط تحويل الـcron القديم من `agent-tick` إليها.
