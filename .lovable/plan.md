# خطة تخزين مشاريع وكيل البرمجة وربطها بـ GitHub

## الهدف
نجعل كل مشروع ينشئه وكيل البرمجة مساحة عمل دائمة داخل Megsy، لها شجرة ملفات قابلة للتصفح، ومستودع خاص في حساب Megsy المركزي، مع ظهور خطة التنفيذ للمستخدم قبل الموافقة وعدم ضياع الملفات عند توقف بيئة التشغيل.

## ما سيتم بناؤه

### 1. إظهار خطة التنفيذ قبل الموافقة
- عرض خطوات الخطة الموجودة حاليًا داخل بطاقة الوكيل فوق زر «موافق، ابدأ التنفيذ».
- إظهار حالة واضحة لكل خطوة أثناء التنفيذ: منتظرة، جارية، مكتملة، أو فشلت.
- إبقاء الخطة الظاهرة هي نفسها التي يوافق عليها المستخدم.

### 2. تخزين داخلي دائم لكل مشروع
- اعتماد `dev_projects` كسجل المشروع و`ai_project_files` كمصدر دائم لمحتوى الملفات.
- إضافة القيود والفهارس وسياسات RLS اللازمة بحيث لا يرى أو يعدّل المستخدم إلا مشاريعه.
- عند إنشاء مشروع جديد، تُحفظ الملفات الأساسية فورًا في قاعدة البيانات بدل الاعتماد على الـ VM المؤقت وحده.
- كل كتابة أو حذف من الوكيل تُحدّث ملف المشروع في قاعدة البيانات مباشرة، مع الاحتفاظ بوقت آخر تعديل.
- عند إعادة تشغيل VM أو فقدانه، يُعاد تكوين المشروع من الملفات الداخلية تلقائيًا ثم يستكمل الوكيل العمل.

### 3. قالب أساسي جاهز
- إضافة قالب React 18 + Vite + TypeScript + Tailwind داخل النظام يشمل ملفات التشغيل والإعدادات والهيكل الأساسي للتطبيق.
- عند إنشاء مشروع، تُنسخ هذه الملفات إلى مساحة المشروع وإلى بيئة التنفيذ قبل بدء التعديلات.
- عند استيراد مشروع موجود، نستخدم ملفاته كما هي ولا نفرض القالب فوقها.

### 4. شجرة ملفات داخل واجهة Megsy
- إضافة لوحة ملفات مرتبطة بالمشروع تعرض المجلدات والملفات بشكل هرمي.
- فتح الملف يعرض محتواه، مع دعم إنشاء ملف/مجلد، تعديل الاسم، الحفظ، والحذف.
- تحديث الشجرة أثناء عمل الوكيل لتظهر الملفات الجديدة فورًا.
- ربط بطاقة نتيجة وكيل البرمجة بالمشروع الحقيقي بدل الاعتماد على ملفات مستخرجة من نص الرسالة أو `localStorage`.

### 5. مستودع GitHub مركزي لكل مشروع
- ربط حساب/منظمة Megsy المركزية عبر GitHub App Connector واستخدامه من كود سيرفر فقط.
- إنشاء مستودع خاص تلقائيًا عند إنشاء المشروع باسم فريد وآمن، وتخزين رابط واسم المستودع في `dev_projects`.
- بعد نجاح كل مجموعة تعديلات والبناء، إرسال الملفات من التخزين الداخلي إلى فرع `main` بعملية commit واحدة.
- حفظ SHA آخر commit وعرض حالة المزامنة والرابط في واجهة المشروع.
- إذا تعطل GitHub، يبقى الحفظ الداخلي ناجحًا وتظهر حالة «غير متزامن» مع إمكانية إعادة المحاولة؛ لا يفشل عمل الوكيل ولا تضيع الملفات.

### 6. إصلاح خطأ حفظ الملفات الحالي
- إلغاء اعتماد وكيل البرمجة على مسار artifact العام غير المجهز لحفظ ملفات المشاريع.
- توجيه `write_file` و`read_file` و`delete_file` الخاصة بالمشاريع إلى مخزن المشروع الدائم، مع المزامنة إلى VM.
- الإبقاء على الملفات القابلة للتنزيل العامة كمسار منفصل للمهام غير البرمجية، باستخدام bucket مخصص بدل bucket باسم `public`، وإظهار رسالة الخطأ الأصلية عند الفشل بدل “could not save the file”.

## التدفق النهائي
```text
طلب المستخدم
  → إنشاء مشروع + ملفات القالب في التخزين الداخلي
  → إنشاء مستودع خاص في GitHub المركزي
  → عرض الخطة والموافقة
  → تشغيل الوكيل داخل VM
  → كل كتابة: VM + ai_project_files
  → بناء وتحقق
  → commit/push إلى GitHub
  → شجرة الملفات والمعاينة تتحدثان للمستخدم
```

## التفاصيل التقنية
- تحديث مسار Dev Agent ليُرجع `project_id` وبيانات المستودع والملفات ضمن الحالة.
- إضافة طبقة server-side موحدة لعمليات الملفات مع التحقق من المسارات ومن ملكية المشروع، وعدم قبول `user_id` من العميل.
- إنشاء migration فقط للتعديلات البنيوية وسياسات الوصول، مع `GRANT` صريح لكل جدول متأثر.
- استخدام GitHub gateway من Edge Function/Server API فقط؛ لا تُرسل مفاتيح الحساب المركزي للمتصفح.
- جعل قاعدة البيانات مصدر الحقيقة، والـ VM مساحة تنفيذ قابلة لإعادة الإنشاء، وGitHub نسخة إصدار ومزامنة خارجية.

## التحقق
- إنشاء مشروع جديد والتأكد من ظهور الخطة وأزرار الموافقة.
- التأكد من وجود ملفات القالب في الشجرة قبل أول تعديل.
- تعديل وإنشاء وحذف ملفات من الوكيل ومن المحرر ثم إعادة تحميل الصفحة والتأكد من بقائها.
- محاكاة VM جديد والتأكد من استعادة المشروع وبنائه.
- التأكد من إنشاء مستودع خاص في حساب Megsy ووصول commit بعد نجاح البناء.
- تعطيل GitHub مؤقتًا والتأكد من استمرار الحفظ الداخلي وإمكانية إعادة المزامنة بدون فقدان البيانات.
- اختبار RLS بمحاولة مستخدم آخر قراءة أو تعديل ملفات المشروع ورفضها.
